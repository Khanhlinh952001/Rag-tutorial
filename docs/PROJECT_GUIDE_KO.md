## 1. 프로젝트 소개

### 이 프로젝트는 뭐예요?

**우리 회사·학교 자료(파일, 웹 페이지, DB 테이블)를 AI에게 ‘공부’시키고, 그 내용만 가지고 질문에 답하는 웹 서비스**를 만드는 예제예요.

- 📁 PDF, 워드 같은 **파일**을 올릴 수 있어요.
- 🌐 **웹 주소**로 글을 가져와서 배울 수 있어요.
- 🗄️ **외부 데이터베이스** 안의 글도 연결할 수 있어요.
- 💬 그 다음 **일반 사용자는 채팅**으로 질문하고, **관리자는 문서와 설정**을 관리해요.

### 어떤 문제를 풀어 주나요?

| 고민 | 이 프로젝트가 하는 일 |
|------|----------------------|
| “챗GPT는 우리 회사 내부 문서를 몰라요” | **우리가 넣은 자료만** 보고 답하게 만들어요 (RAG). |
| “파일이 너무 많아서 사람이 다 읽을 수 없어요” | 파일을 잘게 나누고, **비슷한 질문에 필요한 조각만** 꺼내 와요. |
| “웹에만 있는 공지도 알려 주고 싶어요” | URL로 글을 가져와 **같은 방식으로 학습**할 수 있어요. |

### 사용자는 뭐 할 수 있어요?

| 역할 | 할 수 있는 것 (대표) |
|------|---------------------|
| **일반 사용자** | 로그인 후 **AI 채팅** (`/chat`). 긴 글 대신 **한 줄에 URL만** 붙여 넣으면 그 페이지를 학습한 뒤 답변할 수 있어요. |
| **관리자** | 문서 업로드, 웹·사이트 스캔, 외부 DB 연결, 문서 삭제 등 (`/admin/...`). |

### 전체 흐름 — 한 번에 보기

```text
[사용자] 파일·URL 넣기
    → [웹 화면] 백엔드로 전송
    → [백엔드] 글자 뽑기 → 잘게 자르기 → 숫자로 바꾸기(임베딩)
    → [벡터 DB] 조각들을 “의미 주소록”에 저장
[사용자] 질문
    → 비슷한 조각 찾기 → AI가 질문+조각으로 답 생성
    → [화면] 답 보여 주기
```

비유하자면: **도서관에 책을 넣은 다음(학습), 책 내용만 보고 숙제를 도와주는 선생님(AI)** 과 비슷해요.

## 2. 전체 아키텍처 — 학교 비유로 이해하기

**아키텍처** = “건물을 어떤 방으로 나누고, 누가 무슨 일을 하는지” 그림이에요.

### 큰 그림 표

| 부분 | 한 줄 설명 | 쉬운 비유 |
|------|------------|-----------|
| **Frontend** (Next.js) | 우리가 클릭하는 **웹 화면** | 🏫 **학교 정문·교실 앞 게시판** — 글을 읽고, 버튼을 누르면 선생님(서버)에게 말을 전해요. |
| **Backend** (NestJS) | 규칙대로 일하는 **중앙 사무실** | 🏢 **교무실** — “누가 올린 파일이지?”, “지금 학습 중이야” 같은 처리를 해요. |
| **AI 서버 (OpenAI API)** | 문장을 이해하고 답을 **써 주는 두뇌** | 👨‍🏫 **선생님 두뇌** — 교과서 일부만 보고 답안을 작성해요. (여기서는 OpenAI 회사 컴퓨터가 선생님 역할) |
| **Database** (PostgreSQL) | 회원, 문서 목록, 채팅 내용 등 **표로 정리한 기록** | 📝 **학교 행정실 장부** — 누가 누구인지, 어떤 과제를 냈는지 적어 둬요. |
| **Vector Database** (Qdrant 또는 pgvector) | “비슷한 말이 들어 있는 조각”을 **빨리 찾는 색인** | 📇 **도서관 카드 목록 + 색인 상자** — “공룡”이라고 찾으면 공룡이 나오는 책 근처를 바로 집어요. |
| **File Storage** (디스크 `uploads/` 등) | 원본 파일이 **실제로 쌓이는 곳** | 🏭 **창고** — 큰 상자(파일)를 그대로 쌓아 두고, 필요할 때 꺼내 읽어요. |

### Redis + BullMQ (작업 줄)

| 부분 | 비유 |
|------|------|
| **Redis** | 🔔 **현관 벨 옆 메모판** — “지금 처리할 일 번호”를 빠르게 적어 둬요. |
| **BullMQ** | 📋 **순서대로 처리하는 대기 줄** — 파일이 많을 때 한꺼번에 하지 않고 **한 건씩** 처리해요. |

## 3. 사용한 기술 — 하나씩 풀어 쓰기

아래는 모두 같은 형식이에요: **무엇 / 왜 / 이 프로젝트에서 / 비유 / 장점 / 단점**

### Next.js

| 항목 | 설명 |
|------|------|
| **이것은?** | React로 웹 페이지를 만들 때 쓰는 **프레임워크**예요. “다음 페이지”를 만들기 좋게 도와줘요. |
| **왜?** | 화면 전환, 빠른 개발, 배포에 강해요. |
| **역할** | 사용자·관리자 **웹 UI** (`fe/`). |
| **비유** | 레고로 집을 짓는 **설명서 세트**가 있으면 방 만들기가 쉬운 것과 같아요. |
| **장점** | 익숙한 사람 많음, 문서 많음. |
| **단점** | 처음에는 개념(서버·클라이언트)이 조금 많아요. |

### NestJS

| 항목 | 설명 |
|------|------|
| **이것은?** | Node.js용 **백엔드 집 꾸미기 틀**이에요. “문서 API는 여기, 사용자 API는 여기”처럼 정리해요. |
| **왜?** | 기능이 커질수록 파일이 **역할별로** 나뉘어야 관리가 쉬워요. |
| **역할** | `be/` — 업로드, 채팅, 문서, 인증 등 **모든 서버 로직**. |
| **비유** | 학교에 **과별 교무실**이 나뉘어 있는 것. |
| **장점** | 구조가 깔끼, TypeScript와 잘 맞음. |
| **단요** | 처음엔 장식(데코레이터) 문법이 낯설 수 있어요. |

### PostgreSQL

| 항목 | 설명 |
|------|------|
| **이것은?** | 데이터를 **행과 열 표**로 아주 안전하게 저장하는 DB예요. |
| **왜?** | 회원, 문서, 채팅은 **정확히** 들어 맞아야 해요. |
| **역할** | Prisma 모델 전부의 **집**. |
| **비유** | **엑셀을 여러 장 쌓아 둔 은행 장부** — 숫자와 글자를 안 흐리게 보관. |
| **장점** | 믿음직, 규칙(트랜잭션) 강함. |
| **단점** | “의미로만 비슷한 것 찾기”는 **벡터 DB**와 함께 쓸 때 더 좋아요. |

### Prisma ORM

| 항목 | 설명 |
|------|------|
| **이것은?** | DB와 대화할 때 **SQL을 직접 덜 쓰게** 해 주는 도구예요. |
| **왜?** | 실수를 줄이고, TypeScript와 타입이 맞아요. |
| **역할** | `schema.prisma`에 표 구조를 정의하고, 코드에서 `findMany` 같은 걸 써요. |
| **비유** | 외국어(SQL) 대신 **우리말로 주문**하면 번역기가 DB에 전달해요. |
| **장점** | 타입 안전, 마이그레이션 편함. |
| **단점** | 아주 복잡한 SQL은 가끔 직접 써야 해요. |

### OpenAI API

| 항목 | 설명 |
|------|------|
| **이것은?** | OpenAI公司的 **인터넷으로 연결된 AI 두뇌** 예요. |
| **왜?** | 우리가 집에 슈퍼컴퓨터를 두지 않아도 **멀리 있는 모델**을 빌려 쓸 수 있어요. |
| **역할** | 답글 쓰기, (설정에 따라) 임베딩 만들기. |
| **비유** | **전화로 전문가에게 물어보기** — 우리는 질문과 자료만 보내요. |
| **장점** | 품질 좋은 언어 이해. |
| **단점** | **비용**, 인터넷 끊기면 문제, API 키 필요. |

### RAG (Retrieval-Augmented Generation)

| 항목 | 설명 |
|------|------|
| **이것은?** | **먼저 관련 자료를 찾아오고(Retrieval)**, 그걸 보고 글을 생성(Generation)하는 방식이에요. |
| **왜?** | AI가 **없는 사실을 지어내는 것**을 줄이고, **우리 자료**에 가깝게 답하게 해요. |
| **역할** | 이 프로젝트의 **핵심 동작 원리**. |
| **비유** | 시험에 **교과서 해당 페이지만 펼쳐 놓고** 풀게 하는 것. |
| **장점** | 사내·사이트 정보 반영. |
| **단점** | 자료가 없으면 답도 약해져요. |

### Vector Database (벡터 DB)

| 항목 | 설명 |
|------|------|
| **이것은?** | 글 조각을 **숫자 벡터(좌표)**로 바꿔 두고, “질문과 비슷한 방향”을 빨리 찾는 저장소예요. |
| **왜?** | 단어가 달라도 **비슷한 뜻**을 찾기 좋아요. |
| **역할** | 환경 변수로 **Qdrant** 또는 **PostgreSQL + pgvector** 선택. |
| **비유** | 지도에서 **가까운 이웃 집**을 찾는 것. 글도 수천 차원 좌표로 “가까운 글”을 찾아요. |
| **장점** | 의미 검색에 강함. |
| **단점** | 일반 표 DB만큼 “정확히 같은 문자열” 찾기에는 부적합할 때 있음. |

### Qdrant 또는 pgvector

| 항목 | 설명 |
|------|------|
| **Qdrant** | 벡터만 잘 다루는 **전용 상자**. Docker로 `6333` 포트에 띄울 수 있어요. |
| **pgvector** | PostgreSQL 안에 **‘벡터 열’을 추가한 확장**이에요. DB 하나로 표+검색 가능. |
| **이 프로젝트** | `VECTOR_STORE` 환경 변수로 선택합니다 (`qdrant` / `pgvector`). |
| **비유** | Qdrant = **전문 도구 서랍** / pgvector = **기존 책장에 색인 칸을 더한 것**. |

### Redis

| 항목 | 설명 |
|------|------|
| **이것은?** | 메모리에 **아주 빠르게** 읽고 쓰는 저장소예요. |
| **왜?** | 작업 큐(BullMQ)가 “누가 다음 차례인지” 기억하려면 빠른 메모판이 필요해요. |
| **역할** | 큐/락 등에 사용 (Docker `6379`). |
| **비유** | **칠판에 번호표** 적어 두는 것. |
| **장점** | 속도. |
| **단점** | 전원 끄면 설정에 따라 날아갈 수 있어요 — 중요한 영구 데이터만 넣으면 안 돼요. |

### BullMQ

| 항목 | 설명 |
|------|------|
| **이것은?** | **작업 대기열**을 만드는 라이브러리예요. |
| **왜?** | 파일이 크면 처리 시간이 길어져요. 사용자는 “접수만” 하고, 뒤에서 천천히 해도 돼요. |
| **역할** | 문서 처리 **비동기 작업**에 사용. |
| **비유** | 은행 **번호표 뽑고 창구에서 순서대로** 처리. |
| **장점** | 서버가 버티지 않음. |
| **단점** | Redis가 필요하고, 실패 재시도 설계를 해야 해요. |

### Docker

| 항목 | 설명 |
|------|------|
| **이것은?** | 프로그램을 **상자(컨테이너)**에 넣어서, 누구 컴퓨터에서나 비슷하게 돌게 해요. |
| **왜?** | “내 컴에서는 되는데…”를 줄여요. |
| **역할** | `docker-compose.yml`로 DB, Qdrant, Redis, Tika 등 실행. |
| **비유** | 도시락 **밀폐 용기** — 안 음식(프로그램)이 밖 환경에 덜 흔들려요. |
| **장점** | 팀원과 동일 환경. |
| **단점** | Docker 설치·용량 필요. |

### AWS 또는 서버 구조

| 항목 | 설명 |
|------|------|
| **이 튜토리얼** | 기본은 **내 컴퓨터 + Docker**예요. |
| **나중에** | 같은 도구를 **AWS, GCP 등 클라우드 VM**에 올리면 “인터넷 어디서나” 쓸 수 있어요. |
| **비유** | 지금은 **집에서 가게 장난감**, 클라우드는 **진짜 가게에 간판 달기**. |

### Tailwind CSS

| 항목 | 설명 |
|------|------|
| **이것은?** | 클래스 이름으로 **색·간격·글자 크기**를 빠르게 주는 CSS 도구예요. |
| **왜?** | 디자인 파일을 짧게 쓰고, 화면이 일정하게 예뻐요. |
| **역할** | `fe/` UI 스타일. |
| **비유** | 옷에 **스티커 라벨**을 붙이는 것 — “파란 배경”, “글자 크게”. |
| **장점** | 빠른 작업. |
| **단점** | HTML이 길어 보일 수 있어요. |

### shadcn/ui + Radix

| 항목 | 설명 |
|------|------|
| **이것은?** | 버튼, 대화상자 같이 **잘 만든 UI 조각**을 복사해 쓰는 스타일이에요. |
| **왜?** | 접근성(키보드·스크린 리더)이 좋고, 예쁜 기본 디자인이 있어요. |
| **역할** | 관리자·채팅 화면의 **Button, Input** 등. |
| **비유** | 가구점에서 **완성된 서랍** 사다 조립. |

### TypeScript

| 항목 | 설명 |
|------|------|
| **이것은?** | JavaScript에 **타입(이건 숫자, 이건 글자)**을 더한 언어예요. |
| **왜?** | 실수를 **코딩하는 순간**에 많이 잡아요. |
| **역할** | `fe/`, `be/` 거의 전부. |
| **비유** | 숙제에 **문제 유형을 미리 적어 주는 것**. |

### JWT 인증

| 항목 | 설명 |
|------|------|
| **이것은?** | 로그인 성공 시 **짧은 암호화된 표(**토큰**)**를 주고, 다음 요청마다 “나 맞아요”라고 보여요. |
| **왜?** | 매번 비밀번호를 보내면 위험해요. |
| **역할** | `/auth/login`, 채팅·관리자 API 보호. |
| **비유** | 놀이공원 **손목 밴드** — 하루 동안 입장 증명. |
| **장점** | 서버가 세션을 덜 들고 가도 됨. |
| **단점** | 토큰 탈취 시 대응(만료·HTTPS) 필요. |

### PDF Parser (pdf-parse 등)

| 항목 | 설명 |
|------|------|
| **이것은?** | PDF 파일에서 **글자를 읽어 내는** 도구예요. |
| **왜?** | PDF는 사진처럼 보이지만 실제로는 구조가 복잡해요. |
| **역할** | 업로드 문서 텍스트 추출에 사용. |
| **비유** | 스캔한 책에서 **글자만 타이핑으로 옮기기**. |

### OCR (광학 문자 인식)

| 항목 | 설명 |
|------|------|
| **이것은?** | **이미지 속 글자**를 컴퓨터가 읽는 기술이에요. |
| **왜?** | 슬라이드가 이미지로만 되어 있으면 글이 안 잡혀요. |
| **이 프로젝트** | 예: PPTX 처리 시 환경 변수로 OCR을 켤 수 있는 설계가 있어요. HWP는 **Apache Tika** 서버로 추출해요. |
| **비유** | 사진 속 간판을 보고 **손으로 베껴 쓰기**. |
| **장점** | 스캔 자료도 가능해짐. |
| **단점** | 느리고, 가끔 오타. |

### Embedding (임베딩)

| 항목 | 설명 |
|------|------|
| **이것은?** | 글을 **숫자 나열(벡터)**로 바꿔 “의미의 위치”를 나타내요. |
| **왜?** | 비슷한 말은 비슷한 숫자에 가깝게 가요. |
| **역할** | 검색·RAG의 핵심 전처리. |
| **비유** | 사람 성향 테스트로 **점수**를 내서 비슷한 사람을 찾는 것. |
| **장점** | 의미 검색. |
| **단점** | 비용·시간, 모델마다 느낌이 달라요. |

### Chunking (청킹)

| 항목 | 설명 |
|------|------|
| **이것은?** | 긴 글을 **작은 조각**으로 자르는 일이에요. |
| **왜?** | AI 한 번에 몇 만 자를 다 넣기 어렵고, **필요한 부분만** 골라 쓰기 좋아요. |
| **역할** | 문서·웹 텍스트를 일정 크기로 나눈 뒤 각각 임베딩. |
| **비유** | 긴 연설문을 **문단 카드**로 나누기. |
| **장점** | 검색 정밀도↑. |
| **단점** | 너무 잘게 자르면 문맥이 끊겨요 — 크기 조절이 중요해요. |

## 4. AI가 일하는 순서 — 9단계

아래는 **일반적인 RAG 파이프라인**이에요. (웹 한 줄 URL만 채팅에 넣는 경우 등 일부는 순서가 조금 다를 수 있어요.)

| 단계 | 실제로 하는 일 | 왜 필요해요? | 비유 | 작은 예시 |
|------|----------------|-------------|------|-----------|
| **1. 업로드** | 사용자가 파일이나 URL을 보냄 | AI가 읽을 재료를 줌 | 도서관에 책 기부 | PDF를 “추가” 버튼으로 올림 |
| **2. 서버가 받기** | 파일을 디스크 등에 저장, 정보를 DB에 적음 | 나중에 “어떤 파일인지” 찾을 수 있음 | 창고에 상자 번호 붙이기 | `uploads/` 폴더 + `Document` 행 생성 |
| **3. 텍스트 추출** | PDF/한글/HTML 등에서 글자만 뽑음 | AI는 글자가 있어야 읽음 | 책에서 그림만 빼고 글만 타이핑 | `pdf-parse`, `cheerio`(HTML) 등 |
| **4. Chunk** | 긴 글을 여러 조각으로 자름 | 한 번에 다 넣으면 너무 김, 검색도 어려움 | 과일을 한 입 크기로 자르기 | 500~수천 자 단위 조각 |
| **5. Embedding** | 조각마다 숫자 벡터 생성 | “의미가 비슷한지” 컴퓨터로 비교 | 각 조각에 **좌표** 붙이기 | 벡터 1536차원 같은 배열 |
| **6. Vector DB 저장** | 벡터와 원문 조각을 함께 저장 | 질문 올 때 빠르게 이웃 찾기 | 색인 카드 장에 넣기 | Qdrant 또는 pgvector |
| **7. 질문** | 사용자가 채팅에 글을 씀 | 답의 방향이 정해짐 | 선생님에게 질문 카드 전달 | “이 문서 요점이 뭐야?” |
| **8. 검색** | 질문도 임베딩해서 비슷한 조각 **top-K**개 고름 | 관련 없는 100페이지를 AI에 안 넣기 | 시험 범위만 교과서에서 뜯어 오기 | 상위 5~10개 조각 |
| **9. 답 생성** | 질문 + 조각을 OpenAI에 보내 **답글 문장** 생성 | 사람이 읽기 좋은 완성 답 | 열린 책 보고 요약 숙제 쓰기 | 마크다운으로 답변 |

## 6. API — 문 밖으로 나가는 주문서

**API**는 **식당 주문서** 같아요.  
“메뉴 번호 3, 아이스크림 빼고”라고 **정해진 형식**으로 적으면, 주방(서버)이 이해해요.

### 인증

| API | 무슨 일? | 쉬운 말 |
|-----|----------|---------|
| `POST /auth/register` | 회원가입 | 학교에 **이름 등록** |
| `POST /auth/login` | 로그인 | **출입증(토큰)** 받기 |
| `GET /auth/me` | 내 정보 | **내 학생증** 확인 |

**요청 예시 (로그인)**

```json
POST /auth/login
{
  "email": "user@example.com",
  "password": "비밀번호"
}
```

**응답 예시**

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIs...",
  "user": { "id": "...", "email": "...", "role": "USER" }
}
```

### 채팅 (로그인 필요)

| API | 무슨 일? |
|-----|----------|
| `POST /ai-chat/ask` | 질문 → RAG 답변 + 대화 저장 |
| `POST /ai-chat/search` | 검색만 (답 생성 없이 조각 확인) |
| `GET /ai-chat/my-conversations` | 내 대화 목록 |
| `GET /ai-chat/my-conversations/:id` | 대화 내용 전부 |

**요청 예시 (`ask`)**

```json
POST /ai-chat/ask
Authorization: Bearer <토큰>

{
  "question": "휴가 규정에서 연차는 며칠이야?",
  "conversationId": "(선택) 이전 대화 이어가기"
}
```

**응답에 들어갈 수 있는 것**

```json
{
  "conversationId": "clx...",
  "answer": "...(마크다운 답변)...",
  "retrieved": [ { "content": "...", "score": 0.82 } ],
  "urlIngest": { "ingested": true, "url": "https://..." }
}
```

> 채팅창에 **한 줄로 URL만** 보내면, 이 프로젝트는 그 주소를 **학습한 뒤** 답을 만들 수 있어요.

### 문서·업로드 (관리자 흐름과 연동)

| API | 무슨 일? |
|-----|----------|
| `POST /uploads/document` 등 | 파일 업로드·문서 생성 |
| `POST /documents/from-web` | URL 한 페이지(또는 옵션에 따라 사이트) 학습 |
| `POST /documents/discover-web` | 같은 사이트 링크 **탐색 목록** |
| `GET /documents` | 문서 목록 |

(정확한 본문은 컨트롤러의 DTO를 보면 돼요.)

### 관리자 지식 소스

| API | 무슨 일? |
|-----|----------|
| `GET/POST /admin/knowledge-source/config` | 외부 DB 연결 정보 |
| `POST /admin/knowledge-source/sync` | DB 내용 동기화·학습 |

## 7. 데이터베이스 — 무엇을 저장하나요?

### 왜 DB가 필요해요?

브라우저를 꺼도 **다시 와야** 하니까, 회원·문서·채팅은 **서버 하드/클라우드 표**에 꼭 적어야 해요.

### 주요 표(테이블) 쉬운 설명

| 표 이름 | 들어 있는 것 | 비유 |
|---------|----------------|------|
| **User** | 이메일, 비밀번호(암호화), 역할(USER/ADMIN) | **학생·교사 명단** |
| **Document** | 제목, 파일 경로, 상태(대기/완료/실패), 업로더 | **도서관 책 등록 부** |
| **DocumentChunk** | 잘게 자른 글, 벡터 ID 등 | **책 속 문단 카드** |
| **Conversation** | 대화방 제목, 누구 대화인지 | **쪽지 받은 장** |
| **Message** | 사용자 말 / AI 말 내용 | **쪽지 내용** |
| **ProcessingJob** | 지금 문서가 어느 단계인지 | **진행률 표** |
| **KnowledgeSourceConfig** | 외부 DB 주소·테이블 이름 | **다른 도서관 연락망** |

**임베딩 숫자 자체**는 주로 **Vector DB** 쪽에 두고, PostgreSQL에는 **조각 내용·vectorId**처럼 연결 정보를 둡니다.

## 8. RAG 설명 — 책 찾기로 이해하기

### RAG가 뭐예요?

**R**etrieval = 찾아오기, **A**ugmented = 보강해서, **G**eneration = 생성.  
즉, **찾아온 글 + 질문**으로 답을 써요.

### ChatGPT만 쓰는 것과 차이

| | 일반 ChatGPT | RAG 넣은 우리 서비스 |
|---|--------------|----------------------|
| 학습 데이터 | 인터넷 전체 기준(대략) | **우리가 넣은 문서·웹** 위주 |
| 최신 사내 규정 | 모를 수 있음 | 넣으면 **알 수 있음** |
| 지어내기 | 가끔 있음 | 자료를 주면 **줄임** |

### 왜 필요해요?

회사 내부 규정, 우리 팀만의 매뉴얼은 **공개 인터넷에 없어요**. RAG는 그걸 “교과서”로 펼쳐 놓는 것과 같아요.

### 장점 / 단점 / 언제 쓰나

| 장점 | 단점 |
|------|------|
| 사실에 가깝게 | 자료 준비·품질 관리 필요 |
| 출처 조각을 골라 쓸 수 있음 | 자료가 없으면 답도 약함 |

**언제?** 사내 문서, 고객 지원 매뉴얼, 사이트 공지 같이 **우리만의 글**이 중요할 때.

### 비유 한 줄

**도서관에서 “공룡”이 나오는 페이지만 펼쳐 놓고** 질문에 답하는 것!

## 9. 실행 방법 — 따라 하기

### 0) 준비물

- **Node.js** + **pnpm** 설치  
- **Docker Desktop** (DB를 쉽게 띄울 때)

### 1) 저장소 받기

```bash
git clone <이-프로젝트-주소>
cd Rag-tutorial
```

### 2) Docker로 PostgreSQL · Redis · Qdrant · Tika 켜기

```bash
cd be
docker compose up -d
```

- PostgreSQL: 예시로 `localhost:5433` (compose 파일의 포트 매핑 확인)
- Redis: `6379`
- Qdrant: `6333`
- Tika: `9998`

### 3) Backend 설정

`be/.env` 파일에 **DB 주소**, **JWT 비밀**, **OpenAI API 키**, 필요 시 **REDIS**, **VECTOR_STORE** 등을 적어요.  
(`.env`는 Git에 올리지 마세요!)

예시 (값은 본인 환경에 맞게):

```env
DATABASE_URL="postgresql://admin:123456@localhost:5433/myapp"
JWT_SECRET="길고-난수-같은-문자열"
OPENAI_API_KEY="sk-..."
PORT=3002
REDIS_URL="redis://localhost:6379"
VECTOR_STORE=pgvector
```

Prisma:

```bash
cd be
pnpm install
pnpm run db:generate
pnpm run db:migrate
pnpm run db:seed
pnpm run dev
```

브라우저에서 `http://localhost:3002` 로 헬스 확인 가능.

### 4) Frontend

```bash
cd fe
pnpm install
cp .env.example .env.local
# .env.local 안의 NEXT_PUBLIC_API_BASE_URL=http://localhost:3002 확인
pnpm run dev
```

기본 포트는 **3003** (`package.json`의 `next dev -p 3003`).

### 5) 간단 테스트 순서

1. 브라우저에서 `http://localhost:3003`  
2. 회원가입/로그인 (백엔드 시드에 관리자가 있을 수 있음 — seed 파일 확인)  
3. `/chat`에서 질문  
4. `/admin`에서 문서 업로드(관리자 계정일 때)

## 10. 자주 나는 실수 & 해결

| 증상 | 자주 원인 | 해결 팁 |
|------|------------|---------|
| `OPENAI` 오류 | 키 없음·만료·한도 | `.env` 키 확인, 대시보드에서 사용량 확인 |
| DB 연결 실패 | Docker 안 켜짐, 포트/비번 틀림 | `docker compose ps`, `DATABASE_URL` 다시 확인 |
| CORS/네트워크 오류 | FE 주소와 API 주소 불일치 | `NEXT_PUBLIC_API_BASE_URL`이 백엔드와 같나요? |
| Chunk가 너무 크다/작다 | 설정·파일 종류 | 청크 크기·오버랩 설정 검토 |
| 임베딩 비용 걱정 | 질문·문서가 많음 | 상위 K 줄이기, 캐시, 작은 모델 검토 |
| HWP 오류 | Tika 컨테이너 꺼짐 | Docker `tika` 실행, `TIKA_URL` 확인 |
| 벡터가 비었음 | 아직 학습 안 됨 | 문서 상태가 COMPLETED인지 확인 |

## 11. 나중에 서비스를 키우려면

**비유**: 초반엔 **반 당 학급**, 나중엔 **여러 반**이 되면 급식실·복도도 넓혀야 해요.

| 주제 | 쉬운 말 |
|------|---------|
| **서버 분리** | 채팅 전용 서버, 파일 처리 전용 서버로 나눔 — **역할별 교실** |
| **Load Balancing** | 손님을 여러 계산대로 나눔 — **은행 번호표 여러 창구** |
| **Queue** | 무거운 일은 줄 세워서 천천히 — 이미 BullMQ 방향 |
| **CDN** | 사진·JS를 세계 곳곳 **캐시 창고**에 복제 — 가까운 곳에서 배달 |
| **Cache** | 자주 묻는 질문 답을 **종이에 미리 적어 둠** — Redis 등 활용 |

**더 깊게**: 동시 접속·월 비용·병목·스케일 아웃을 **숫자까지** 보고 싶다면 → [§12 성능 및 트래픽 처리 가이드](#12-성능-및-트래픽-처리-가이드-비용확장운영) 를 이어서 읽어 보세요.

### 12.1 현재 프로젝트 성능 분석 (구조 기준)

**이 저장소 기술 스택**: Next.js `fe/` · NestJS `be/` · PostgreSQL · Redis(+ BullMQ) · 벡터(Qdrant 또는 pgvector) · OpenAI API · Docker Compose(DB, Redis, Qdrant, Tika 등) · 원본 파일 저장(디스크 `uploads/` 등).

#### “동시 접속”부터 정리

| 표현 | 의미 |
|------|------|
| **동시 접속(웹)** | 브라우저로 사이트를 연 사용자 수 — 로그인·목록·정적 리소스 위주면 **가벼운 편** |
| **동시 RAG 질문** | `/chat` 등에서 **같은 초에** 백엔드 + OpenAI + 벡터 검색이 도는 요청 수 — 여기가 **무게 중심** |
| **동시 업로드·학습** | 관리자가 PDF 등을 올려 **임베딩 큐**가 돌 때 — **CPU·디스크·OpenAI 임베딩 TPM**을 씀 |

**한 줄 요약**: 이 프로젝트에서 “서버 1~2대”로 말할 때, 보통 **Nest/Next 자체보다 OpenAI·DB 연결·문서 파이프라인**이 먼저 한계에 닿는 경우가 많습니다.

#### 대략 몇 명까지? (왜 그런 숫자인가)

아래는 **한 대의 호스트에 Docker로 Postgres·Redis·Qdrant·Nest·(개발 시 Next)** 를 같이 올린 **작은 환경**을 가정한 **질문(RAG) 동시성**입니다. “10명·100명”은 **동시에 답을 기다리는 질문**에 가깝게 읽으면 됩니다.

| 동시 RAG 질문(겹침) | 가능 여부·느낌 | 왜 그렇게 추정했나요? |
|---------------------|----------------|------------------------|
| **~10명** | **대부분 괜찮음** (가끔 느림) | 질문 1건이 보통 **수 초**인데, 큐·풀 설정만 맞으면 **한도 전**에 소화되는 경우가 많음 |
| **~100명** | **설계 따라 들쑥날쑥** | OpenAI **RPM/TPM**, Postgres **커넥션**, `topK`·청크 길이에 따라 **대기열**이 생김 |
| **~1,000명** | **단일 API 서버 1대**로는 보통 어려움 | 동시에 수천 건의 **수 초짜리 외부 API**는 **수평 분리·레이트 리밋·캐시** 없이는 버거움 |
| **~10,000명** | **프로덕션 아키텍처 전제** | 리전·멀티 AZ·오토스케일·관측·DB/벡터 분리·게이트웨이가 기본 |

**CPU / RAM (Docker 한 호스트에 주요 구성 요소를 같이 켤 때의 감각)**

| 구성 | CPU | RAM | 비고 |
|------|-----|-----|------|
| 최소(학습용) | 2 vCPU | **8 GB** | 4GB는 Postgres+Qdrant+Redis가 같이 있으면 **빠듯**한 경우가 많음 |
| 권장(로컬·소형) | 4 vCPU | **16 GB** | Tika로 큰 파일이 겹치거나 Qdrant 메모리 여유 |
| 소규모 실제 트래픽 | 4~8 vCPU | **16~32 GB** | 업로드·임베딩 워커 분리를 검토할 즈음 |

**업로드가 많을 때**

| 영향 | 설명 |
|------|------|
| 디스크·CPU | Tika 파싱·(선택) OCR·PDF 페이지 수에 따라 **작업당 수 초~수십 초** |
| 큐 적체 | BullMQ 한 줄이면 **뒤쪽 업로드가 “대기 중”**으로 쌓임 — **워커 수·인스턴스 분리**로 완화 |
| 임베딩 비용·TPM | 청크가 많을수록 **임베딩 API 호출·토큰**이 늘어남 |

**AI 응답 속도(사용자가 느끼는 시간)**

| 구간 | 대략 | 비고 |
|------|------|------|
| 벡터 검색(topK 소량) | **10~100 ms** | 데이터·인덱스·필터에 따라 |
| OpenAI “첫 토큰”까지 (스트리밍 시) | **0.5~4 s** | 모델·혼잡·프롬프트 길이 |
| 짧은 답 전체 | **2~10 s** | 컨텍스트가 길수록 입력 토큰·처리 시간↑ |

#### 규모별(소·중·대) — 무엇이 터지고, 무엇을 준비하나

| 규모(동시 RAG 질문 수의 감각) | 흔한 증상 | 서버·구조 | 최적화 방향 |
|------------------------------|-----------|-----------|-------------|
| **소규모 (대략 ~10~30)** | 가끔 느린 답, 개발 DB 부하 | **1~2대**, Compose 또는 소형 VPC | 청크·`topK`·연결 풀, **gpt-4o-mini**급, 스트리밍 |
| **중규모 (~30~300)** | 429·p95 지연 급증, DB 커넥션 | **API 여러 대 + 로드 밸런서**, Redis/DB **분리** 검토 | 캐시, 큐, PgBouncer, 업로드 워커 분리 |
| **대규모 (수백 동시 RAG 이상)** | 전 구간 장애·비용 폭증 | **멀티 AZ**, 읽기 복제, 벡터·객체 스토리지 분리, **레이트 리밋** | 동일 질문 합류, FAQ 캐시, 배치 임베딩, 비용 알람 |

#### 사용자 수·질문 수·문서에 따른 OpenAI 중심 월 비용 (예시 계산)

**가정 A — 질문 비용**

- 모델: **gpt-4o-mini** 급  
- 공개 단가 예시(변동 가능): **입력 $0.15 / 1M tok**, **출력 $0.60 / 1M tok**  
- 질문 1회: **입력 2,000 tok**(시스템+검색된 청크+질문) + **출력 800 tok**  
- 1회 LLM 비용 ≈ \(2000×0.15 + 800×0.6\) / 1,000,000 ≈ **$0.00078** (약 **1.1원 미만**)

| 하루 질문 수 | 월 질문(30일) | LLM만 대략 (위 가정) |
|--------------|----------------|----------------------|
| 100 | 3,000 | ~ **$2.3** |
| 1,000 | 30,000 | ~ **$23** |
| 10,000 | 300,000 | ~ **$234** |
| 100,000 | 3,000,000 | ~ **$2,340** |

**가정 B — 문서(임베딩) 비용**

- `text-embedding-3-small` 예시 **$0.02 / 1M tok**  
- 문서 1건 **40 청크 × 평균 400 tok** = **16,000 tok**  
- 임베딩 비용 ≈ 16,000 × 0.02 / 1,000,000 = **$0.00032 / 문서·1회 전체 임베딩**

| 문서 수 | 임베딩만 대략 (재임베딩 없다고 가정) |
|---------|--------------------------------------|
| 100 | ~ **$0.032** |
| 1,000 | ~ **$0.32** |
| 10,000 | ~ **$3.2** |

→ **질문이 늘수록 비용이 커지는 속도**가, 문서를 한 번 넣는 비용보다 보통 **훨씬 빠릅니다**(단, 청크·재처리를 자주 돌리면 예외).

### 12.5 병목(Bottleneck)

**왜 느려지나요?** 한 시간에 들어오는 일이 **처리 가능한 처리량**을 넘으면 대기열이 생기고, **가장 좁은 관**(병목)에서 묶입니다.

| 요소 | 이 RAG에서 위험도 | 메모 |
|------|-------------------|------|
| **OpenAI API** | 매우 큼 | **RPM/TPM**, 네트워크, 모델 혼잡 |
| **임베딩** | 업로드 폭주 시 큼 | 청크 수=API 호출·토큰 |
| **Vector Search** | 보통 중간 이하 | 데이터·필터·인덱스 커지면↑ |
| **파일 업로드** | 순간적으로 큼 | 디스크·동시 쓰기·백신 스캔 |
| **OCR**(도입 시) | 큼 | 페이지당 비용·시간 |
| **대형 PDF** | 큼 | 메모리·파싱 |

**대표적 완화**

| 수단 | 역할 |
|------|------|
| **캐시(Redis)** | 같은 질문·같은 문서 조합 → **답·검색 결과 재사용** |
| **큐(BullMQ)** | 무거운 건을 **웹 요청 밖**으로 빼 **주문서**만 빨리 받기 |
| **CDN** | JS/CSS/이미지 **가까운 곳**에서 |
| **Load Balancer** | API 서버 **여러 창구**로 분산 |

### 12.6 Scale-Out 구조 (음식점·택배·은행)

| 비유 | 이 프로젝트에 대응 |
|------|-------------------|
| **음식점 주방** | 손님(FE)만 줄 서면 안 되고 **주방(BE·워커)** 이 따라야 함. AI는 **특선 코스 주방** — 주문이 한꺼번에 오면 **번호표(Queue)**가 필수 |
| **택배 물류센터** | 업로드·임베딩은 **입하**, 답변은 **출하 라인** — 센터를 나누면 한쪽이 막혀도 다른 쪽은 돎 |
| **은행 창구** | 로드 밸런서 = **번호표 뽑기** — 창구(API 인스턴스)를 늘리면 동선 분산 |

**실제 기업이 자주 하는 일**

| 분리 | 이유 |
|------|------|
| **프론트** | 정적·SSR·엣지에 가깝게 (Vercel 등) |
| **백엔드 API** | 요청량에 맞게 수평 확장 |
| **AI 워커** | 임베딩·긴 작업이 **HTTP 스레드·풀**을 점유하지 않게 |
| **DB / Vector DB** | CPU·메모리·디스크를 **공유 OS**에서 분리 |
| **Queue** | 트래픽이 **순간 폭주**해도 **유실 없이** 나중에 처리 |

### 12.7 성능 최적화 전략

| 전략 | 왜 빨라지나요? | 체감·비용(대략) |
|------|----------------|-----------------|
| **Redis 캐시** | 같은 질의 반복 시 **외부 호출 생략** | p95 수 초 → **수십 ms급** 가능(적중 시) |
| **Response Streaming** | “첫 글자”까지의 **체감 대기** 감소 | 사용자는 덜 답답함 |
| **Chunk 최적화** | 불필요하게 긴 컨텍스트 방지 | **토큰·지연 동시 절감** |
| **임베딩 재사용** | 파일 해시·버전 동일 시 재계산 생략 | 업로드 비용 **크게** 줄 수 있음 |
| **Lazy Loading** | 처음에 필요한 데이터만 | FE 초기 로딩 개선 |
| **CDN** | 지리적으로 가까운 POP | 정적·캐시 가능 응답 RTT↓ |
| **Pagination** | 한 번에 긁는 행 수 제한 | DB·메모리 보호 |
| **백그라운드 워커·큐** | UI는 “접수만”·처리는 뒤에서 | 업로드 폭주 시 **서비스 전체 멈춤** 완화 |

---

### 12.8 실제 운영 시 발생 가능한 문제

| 문제 | 대응 | 모니터링·로그 |
|------|------|----------------|
| OpenAI 장애·지연 | 재시도·지수 백오프, **짧은 사용자 메시지**, 캐시 | HTTP `429/5xx`, OpenAI 상태 페이지 |
| 트래픽 폭주 | 레이트 리밋, 큐, 오토스케일, **WAF** | RPS, p95/p99, 큐 길이 |
| DB 다운·커넥션 고갈 | 복제·페일오버, PgBouncer, 풀 크기 | “too many connections”, 슬로우 쿼리 로그 |
| Redis 메모리 부족 | `maxmemory-policy`, TTL, 캐시 크기 상한 | `used_memory`, 키 개수 |
| 너무 큰 PDF | 업로드 상한, 페이지 분할, 비동기 | 워커 처리 시간·OOM |
| OCR 느림 | 비동기·전용 엔진·페이지 제한 | 작업별 wall time |
| 동시 대량 업로드 | 사용자·IP당 quota, **백프레셔** | BullMQ 대기열·실패율 |

### 12.9 추천 운영 구조

| 목표 | 현실적인 그림 |
|------|----------------|
| **이 프로젝트로 PoC·내부용** | **단일 호스트 Docker** 또는 **소형 VPS**, 벡터는 pgvector **또는** Qdrant 중 하나, 임베딩·채팅은 **소형 모델** 위주 |
| **비용 대비 효율(소규모 실서비스)** | FE는 **CDN·엣지 가능한 호스**, BE는 **2대+LB**, DB·Redis는 **한 번은 매니지드 또는 분리 인스턴스**로 안정성 확보, **OpenAI·스토리지 예산 알람** |
| **스타트업 추천** | 한국 사용자 위주면 **서울 리전**을 우선 검토, 로그·메트릭·알람은 초기부터 **최소 세트**(CPU·RAM·디스크·5xx·큐 길이·일일 비용) |
| **베트남 사용자 비중이 크면** | 사용 측 RTT를 줄이려 **가까운 리전**(예: 싱가포르 등)에 API를 두고, 필요 시 **다중 리전** 검토 — **법규·개인정보**는 별도 검토 |

**정리**: 이 모노레포는 **확장 가능한 역할 분리(큐·모듈)**를 이미 갖춘 편이라, 트래픽이 늘면 **OpenAI 한도 → DB 연결·쿼리 → 워커·스토리지** 순으로 **병목 후보를 의심**하면 운영이 수월합니다.

## 13. 마무리 요약

### 핵심 한 줄

**“우리만의 책(문서)을 도서관에 넣고, 질문하면 그 책 근처만 보고 AI가 답한다.”**

### 이 프로젝트로 배울 수 있는 것

- 웹 **프론트·백엔드**가 어떻게 이야기하는지 (HTTP, JSON)  
- **DB**에 무엇을 남기는지  
- **RAG**로 “거짓 줄이기 + 우리 자료 반영”을 하는 법  
- **Docker**로 주변 도구(DB, 큐)를 같이 켜는 법  

### 어떤 서비스로 키울 수 있어요?

사내 **규정 Q&A**, **제품 매뉴얼 봇**, **고객 지원 챗봇**, **교육 자료 튜터** 같은 곳에 응용할 수 있어요.
